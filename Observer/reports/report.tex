\section{Real-world Problem \& Motivation}

\subsection{Background: Banking Event Notifications}
In software development, maintaining consistency between core business entities and dependent logging or notification modules is a common requirement. In a simplified banking system, a \texttt{BankAccount} class manages account state, balance updates, and transaction records.

When a customer performs an operation (such as a deposit, withdrawal, or failed overdraft attempt), multiple subsystems need to respond:
\begin{enumerate}
    \item \textbf{User Interface (UI):} Updates the displayed balance and transaction list.
    \item \textbf{Email Service:} Sends transaction receipts and security alerts to the user.
    \item \textbf{Audit Logger:} Writes timestamped audit records for compliance.
    \item \textbf{Fraud Detection Engine:} Evaluates transaction parameters to identify suspicious activities.
    \item \textbf{Mobile Push Service:} Sends alert notifications to the user's mobile device.
    \item \textbf{Analytics Service:} Records transaction data for operational metrics.
\end{enumerate}

\subsection{Problem Statement}
The objective is to allow the \texttt{BankAccount} class to notify multiple interested services when a transaction occurs without coupling the account logic to specific service implementations. Furthermore, services must be able to subscribe or unsubscribe at runtime without requiring changes to existing classes or recompilation of the core banking logic.

\section{Naive Solution}

In a basic implementation, the \texttt{BankAccount} class maintains direct member pointers to each concrete service. When a transaction takes place, \texttt{BankAccount} calls specific methods on each service sequentially.

\begin{lstlisting}[caption=Naive Bank Account with Direct Service Coupling (\texttt{naive.cpp})]
namespace naive {

class UIUpdateService {
public:
    void updateUI(double amount, double balance) {
        std::cout << "[UI] Updated. Transaction: $" << amount << ", Balance: $" << balance << "\n";
    }
};

class EmailService {
public:
    void sendEmail(const std::string& accNum, double amount) {
        std::cout << "[Email] Sent receipt for account " << accNum << ". Amount: $" << amount << "\n";
    }
};

class LoggerService {
public:
    void logTransaction(const std::string& accNum, double amount) {
        std::cout << "[Logger] Logged transaction for " << accNum << ". Amount: $" << amount << "\n";
    }
};

class FraudDetectionService {
public:
    void detectFraud(const std::string& accNum, double amount) {
        std::cout << "[Fraud AI] Checked account " << accNum << " for $" << amount << ". Status: OK.\n";
    }
};

class MobileAppService {
public:
    void pushNotification(double amount) {
        std::cout << "[Mobile App] Push alert sent. Amount: $" << amount << "\n";
    }
};

class AnalyticsService {
public:
    void trackEvent(const std::string& eventType, double amount) {
        std::cout << "[Analytics] Event '" << eventType << "' logged for $" << amount << "\n";
    }
};

// BankAccount directly coupled to concrete service classes
class BankAccount {
private:
    double balance;
    std::string accountNumber;
    
    // Direct dependencies on 6 concrete classes
    UIUpdateService* uiService;
    EmailService* emailService;
    LoggerService* loggerService;
    FraudDetectionService* fraudService;
    MobileAppService* mobileService;
    AnalyticsService* analyticsService;

public:
    BankAccount(std::string accNum,
                UIUpdateService* ui, EmailService* email,
                LoggerService* logger, FraudDetectionService* fraud,
                MobileAppService* mobile, AnalyticsService* analytics)
        : balance(0.0), accountNumber(accNum),
          uiService(ui), emailService(email), loggerService(logger),
          fraudService(fraud), mobileService(mobile), analyticsService(analytics) {}

    void deposit(double amount) {
        balance += amount;
        
        // Explicit dispatch calling each service method directly
        uiService->updateUI(amount, balance);
        emailService->sendEmail(accountNumber, amount);
        loggerService->logTransaction(accountNumber, amount);
        fraudService->detectFraud(accountNumber, amount);
        mobileService->pushNotification(amount);
        analyticsService->trackEvent("deposit", amount);
    }
};

} // namespace naive
\end{lstlisting}

\subsection{Step-by-Step Execution of the Naive Solution}
To illustrate the behavior of the naive implementation, consider depositing $\$500.00$:
\begin{enumerate}
    \item \textbf{Initialization:} The client instantiates all 6 concrete service objects and passes their pointers to the \texttt{BankAccount} constructor.
    \item \textbf{State Update:} Invoking \texttt{bankAccount.deposit(500.0)} increments the internal \texttt{balance} attribute by $\$500.00$.
    \item \textbf{Sequential Dispatch:} The \texttt{deposit()} method executes the following calls:
    \begin{itemize}
        \item \texttt{uiService->updateUI(500.0, 500.0)}
        \item \texttt{emailService->sendEmail("ACC-101", 500.0)}
        \item \texttt{loggerService->logTransaction("ACC-101", 500.0)}
        \item \texttt{fraudService->detectFraud("ACC-101", 500.0)}
        \item \texttt{mobileService->pushNotification(500.0)}
        \item \texttt{analyticsService->trackEvent("deposit", 500.0)}
    \end{itemize}
\end{enumerate}

\section{Introduction to the Observer Design Pattern}

\subsection{Definition and Intent}
According to the Gang of Four (GoF), the \textbf{Observer Pattern} is defined as:
\begin{quote}
\textit{"Define a one-to-many dependency between objects so that when one object changes state, all its dependents are notified and updated automatically."}
\end{quote}

The pattern separates the object that generates events (the \textbf{Subject}) from the objects that handle those events (the \textbf{Observers}) by using an abstract interface.

\subsection{Key Structural Components}
\begin{itemize}
    \item \textbf{Subject (\texttt{BankAccount}):} Maintains a collection of observer pointers and provides subscription methods:
    \begin{itemize}
        \item \texttt{attach(observer)}: Registers a new subscriber.
        \item \texttt{detach(observer)}: Removes a registered subscriber.
        \item \texttt{notify(type, amount)}: Iterates through subscribers and calls their update method.
    \end{itemize}
    \item \textbf{Observer Interface (\texttt{AccountObserver}):} Declares the abstract update method:
    \begin{lstlisting}[language=C++]
virtual void onTransaction(const std::string& type, double amount, double balance) = 0;
    \end{lstlisting}
    \item \textbf{Concrete Observers (\texttt{UIObserver}, \texttt{EmailObserver}, \texttt{LoggerObserver}, etc.):} Implement the interface to execute their specific response logic.
    \item \textbf{Push vs. Pull Notification Models:}
    \begin{itemize}
        \item \textbf{Push Model:} The Subject sends state details (\texttt{type}, \texttt{amount}, \texttt{balance}) directly as method arguments during the notification call.
        \item \textbf{Pull Model:} The Subject passes a reference to itself, and observers query the specific state attributes they need.
    \end{itemize}
\end{itemize}

\section{Pattern-Based Implementation in C++17}

\subsection{Memory Management Considerations}
In C++, managing observer lifetimes requires addressing potential reference issues:
\begin{itemize}
    \item \textbf{Raw Pointers:} If an observer is deleted while remaining in the subject's list, subsequent notifications can result in dangling pointer access.
    \item \textbf{Smart Pointers (\texttt{std::shared\_ptr} and \texttt{std::weak\_ptr}):}
    \begin{itemize}
        \item \textbf{\texttt{std::shared\_ptr}:} Keeps the observer instance valid while it is held in the subject's subscription list.
        \item \textbf{\texttt{std::weak\_ptr}:} Allows the subject to observe whether the subscriber still exists via \texttt{lock()} before invoking callbacks, preventing memory leaks when observers are destroyed externally.
    \end{itemize}
\end{itemize}

\subsection{Source Code Implementation}

\begin{lstlisting}[caption=Observer Interface and BankAccount Subject Implementation (\texttt{pattern.cpp})]
#include <iostream>
#include <memory>
#include <vector>
#include <string>
#include <algorithm>

// Observer Interface
class AccountObserver {
public:
    virtual ~AccountObserver() = default;
    virtual void onTransaction(const std::string& type, double amount,
                               double currentBalance) = 0;
};

// Subject Class
class BankAccount {
public:
    BankAccount(double initialBalance = 0.0) : balance_(initialBalance) {}

    void attach(std::shared_ptr<AccountObserver> observer) {
        observers_.push_back(observer);
    }

    void detach(std::shared_ptr<AccountObserver> observer) {
        observers_.erase(
            std::remove(observers_.begin(), observers_.end(), observer),
            observers_.end()
        );
    }

    void notify(const std::string& type, double amount) {
        for (const auto& observer : observers_) {
            observer->onTransaction(type, amount, balance_);
        }
    }

    void deposit(double amount) {
        balance_ += amount;
        std::cout << "[BankAccount] Deposited $" << amount << ". New balance: $" << balance_ << "\n";
        notify("Deposit", amount);
    }

    void withdraw(double amount) {
        if (amount > balance_) {
            std::cout << "[BankAccount] Rejected: Insufficient funds for withdrawal of $" << amount << "\n";
            notify("FailedWithdrawal", amount);
        } else {
            balance_ -= amount;
            std::cout << "[BankAccount] Withdrew $" << amount << ". New balance: $" << balance_ << "\n";
            notify("Withdrawal", amount);
        }
    }

    double getBalance() const { return balance_; }

private:
    double balance_;
    std::vector<std::shared_ptr<AccountObserver>> observers_;
};
\end{lstlisting}

The execution driver demonstrates attaching all 6 observers, running a deposit, detaching the Email and Mobile App observers at runtime, and verifying the subsequent withdrawal output.

\begin{lstlisting}[caption=Observer Pattern Execution Demo (\texttt{runPatternDemo})]
void runPatternDemo() {
    BankAccount account(1000.0);

    auto ui = std::make_shared<UIObserver>();
    auto email = std::make_shared<EmailObserver>();
    auto logger = std::make_shared<LoggerObserver>();
    auto fraud = std::make_shared<FraudAIObserver>();
    auto mobile = std::make_shared<MobileAppObserver>();
    auto analytics = std::make_shared<AnalyticsObserver>();

    // 1. Attach all 6 observers
    account.attach(ui); account.attach(email); account.attach(logger);
    account.attach(fraud); account.attach(mobile); account.attach(analytics);

    std::cout << "\n--- TEST 1: Deposit $500.00 (All 6 Observers Active) ---\n";
    account.deposit(500.0);

    // 3. Dynamic Detachment
    std::cout << "\n--- TEST 2: Detaching Email & Mobile Observers ---\n";
    account.detach(email);
    account.detach(mobile);

    // 4. Perform Subsequent Withdrawal
    std::cout << "\n--- TEST 3: Withdrawal $200.00 (Email & Mobile Inactive) ---\n";
    account.withdraw(200.0);

\section{Evaluation of Trade-offs}

\subsection{Advantages}
\begin{itemize}
    \item \textbf{Open-Closed Principle (OCP):} New observer classes (such as tax calculators or external reporting tools) can be added without modifying \texttt{BankAccount}.
    \item \textbf{Loose Coupling:} \texttt{BankAccount} depends only on the abstract \texttt{AccountObserver} interface, separating transaction logic from output mechanisms.
    \item \textbf{Runtime Configuration:} Observers can attach or detach dynamically based on application requirements.
    \item \textbf{Broadcast Distribution:} A single state update automatically notifies all registered observers.
\end{itemize}

\subsection{Disadvantages and Limitations}
\begin{itemize}
    \item \textbf{Lapsed Listener Issues:} If observers are destroyed without detaching, the subject may retain inactive references, causing resource leaks or undefined behavior when raw pointers are used.
    \item \textbf{Unordered Notification:} Observers are invoked in list order, so individual observers must not assume specific execution ordering relative to other observers.
    \item \textbf{Cascading Updates:} If an observer calls a method on the subject that triggers another notification, it can lead to unintended recursive updates.
\end{itemize}

\section{Applications}

The Observer pattern is widely applied in software engineering whenever loose coupling between state providers and dependent consumers is required:

\begin{itemize}
    \item \textbf{Graphical User Interface (GUI) Event Systems:} Modern UI toolkits use the Observer pattern to handle user interactions. UI components (such as buttons, sliders, and text fields) serve as event sources, while event handlers register as observers to process clicks, keystrokes, and focus changes.
    \item \textbf{Model-View-Controller (MVC) Architectures:} In MVC (and MVVM architectures), the Model acts as the Subject maintaining application state. Multiple Views register as observers with the Model to automatically update and re-render the display whenever the underlying data changes.
    \item \textbf{Publish-Subscribe and Message-Driven Systems:} Message brokers and event buses implement broadcast distribution where message topics act as subjects and distributed microservices subscribe to receive event payloads asynchronously.
    \item \textbf{State Management and Reactive Data Streams:} Modern state containers and reactive streams allow UI components or backend workers to subscribe to state stores, triggering downstream updates automatically when state changes occur.
    \item \textbf{System Monitoring and Logging Services:} Telemetry pipelines, audit loggers, and health check services attach to critical business processes as observers to record events and detect anomalies without altering core transactional logic.
\end{itemize}

\section{Interpreter and Mediator Integration}

Software architectures rarely utilize design patterns in isolation. The Observer pattern combines with the Interpreter and Mediator patterns to establish decoupled, event-driven, and reactive application pipelines.

\subsection{Combining Observer with the Interpreter Pattern}
In standard evaluation pipelines, expression trees are evaluated on-demand when explicitly triggered by a caller. Integrating the Observer pattern transforms this model into a push-based reactive rule engine.

In this architecture, the evaluation symbol table (\texttt{Context}) functions as an observable Subject. The root nodes of domain-specific Abstract Syntax Trees (ASTs) register as observers listening for updates to specific variable identifiers. Whenever a variable's value changes within the Context, the Context notifies all dependent expression trees. The trees re-evaluate their logical predicates automatically and trigger downstream actions without requiring polling loops or manual re-invocation.

\subsection{Combining Observer with the Mediator Pattern}
In complex systems with multiple interacting components, direct peer-to-peer subscriptions can lead to intricate point-to-point connections. Combining the Observer and Mediator patterns resolves this issue by introducing a centralized Event Aggregator or Event Bus.

Under this model, components do not subscribe directly to each other. Instead, they register as observers with a central \texttt{EventMediator}. When an event occurs, the publishing component sends the event details to the Mediator. The Mediator inspects the event payload, applies routing or filtering policies, and dispatches notifications to the relevant subscriber components. This approach simplifies the communication topology from an $O(N^2)$ mesh to an $O(N)$ star topology while maintaining loose coupling.

\section{Conclusion}
The Observer Design Pattern provides a structured way to decouple state-holding subjects from dependent notification and logging modules. By using an abstract interface and maintaining dynamic subscriber collections, the pattern supports the Open-Closed and Single Responsibility Principles.

In C++17, utilizing smart pointers (\texttt{std::shared\_ptr} and \texttt{std::weak\_ptr}) ensures safe object lifetime management and prevents dangling references. When integrated with the Interpreter and Mediator patterns, the Observer pattern supports reactive rule engines and centralized event-driven architectures.
